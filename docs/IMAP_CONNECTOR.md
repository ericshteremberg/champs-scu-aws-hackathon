# IMAP mailbox connector

Causality supports a customer-configured IMAP mailbox through Connections → Other email provider. Network Solutions customers can use this path without a Google account, developer registration or custom endpoint. The implementation also accepts other public IMAP servers that support mailbox/app-password authentication and implicit TLS on port 993. Provider compatibility is not the same as a completed customer test. No real mailbox has been connected or read during implementation.

## Customer setup

1. Open [Connections](https://causality-hackathon-dev.slidah60.workers.dev/workspace?view=integrations) and choose **Connect other email**.
2. Enter the full mailbox email and click **Find email settings**. The AWS backend looks up public DNS using only the domain. Network Solutions Cloud Mail's documented MX set selects its verified TLS host automatically; a valid `_imaps._tcp` SRV record can identify another provider. Google-hosted mail directs to Gmail OAuth. Microsoft-hosted mail explains that Microsoft OAuth is not implemented. Unknown providers open **Advanced settings** for the exact hostname supplied by the provider. No mailbox login occurs during discovery.
3. Enter a mailbox password or provider-issued app password directly in the form. Prefer an app password where supported. Keep credentials out of chat, screenshots and Git. A credential may authorize more operations than Causality performs. Editing the email or server clears the password and consent.
4. INBOX is included. By default, setup also includes a single selectable Sent folder explicitly identified by the server's SPECIAL-USE extension. It does not guess from names. Missing or ambiguous metadata leaves only INBOX; the saved folders are displayed after connecting. Under **Advanced settings**, supply a Sent folder override or disable automatic Sent discovery. All selected folders must be accessible; none are created or renamed.
5. Review the storage/read-access notice, check the authorization box and click **Test and connect mailbox**. Causality verifies TLS, login and read-only folder access before saving credentials. It does not fetch message bodies during setup. Failed checks do not retain the password; the input clears after submission. Repeated login attempts are limited to one per 30 seconds per workspace.
6. Choose an open case. The displayed search address is the case email, never its customer name. To resolve an address first, use **Find customer account in Supabase**, approve the suggested table's ID/name/email columns once, search for a name or email, and review a matching record. **Use this email and search** saves the reviewed address, clears prior draft approval, and starts IMAP. Duplicate names remain separate choices. Alternatively, search the existing case email directly. The form defaults to all messages in selected folders; a faster newest-500 option remains available. The server filters by From/To and fetches at most ten matching headers per folder, returning ten overall. It checks exact From/To envelope addresses after the server's substring search. It is not a full mailbox audit or a proof of order relevance.
7. Preview a result, review its plain text and case, then **Import reviewed IMAP email**. Import invalidates prior draft approval and makes the previous investigation stale. Run a new investigation when appropriate. Nothing is sent to the customer or submitted to Stripe.
8. **Disconnect IMAP** removes saved credentials and prevents subsequent reads/imports. A request already in flight can finish its network read until its deadline, but cannot save its result after disconnect. Revoke any app password with the provider separately. Imported case evidence remains.

Use the Gmail OAuth connector for Google-hosted mail. Microsoft 365 OAuth, custom ports, plaintext/STARTTLS, non-email usernames, delegated accounts and local-only servers are not supported by this IMAP form. Proton Bridge is not a public hosted mailbox endpoint for this deployment.

## Runtime and data flow

- `components/workspace/imap-provider.tsx` handles setup, explicit access confirmation, case selection, preview/import and disconnect. Passwords exist only in transient form/request memory, never localStorage or sessionStorage. The hosted preview uses the existing shared team login; all people using that login share its connections and imported evidence.
- Same-origin POST `/api/providers/imap` goes through the authenticated Cloudflare bridge to private AWS Lambda. Supported actions are `discover`, `connect`, `disconnect`, `search`, `preview`, and `import`. No new Cloudflare storage is introduced. The local non-AWS route returns `aws_required`.
- `aws/imap-discovery.ts` performs authenticated, password-free DNS discovery with a five-second deadline and at most 50 MX/SRV records considered. Only documented exact provider MX patterns or TLS SRV targets are used; MX is never treated as an IMAP login host. Discovery does not store credentials or modify a connection. Network Solutions has multiple platforms, so unmatched legacy plans use manual settings. Connection still resolves/validates public addresses and checks TLS independently. Automatic Sent detection bounds LIST to 200 folders and accepts only server extension metadata, not library name heuristics.
- `aws/imap-provider.ts` validates strict action schemas, requires workspace ownership and mutable cases, and applies version-conditional DynamoDB transactions. Connection attempts reserve a version before network I/O, so concurrent disconnect or setup cannot restore an old connection.
- Public metadata is projected from `provider#imap`. Login settings/password are stored separately in `provider-token#imap` under the workspace partition, using the existing DynamoDB encryption at rest and IAM-protected backend. This is not a per-mailbox Secrets Manager secret or separate application-layer encryption. Passwords are absent from status, workspace, audit, evidence and model inputs. Network protocol logging is disabled and provider errors are sanitized.
- `imap-selection#<caseId>` and `imap-preview#<caseId>` hold temporary, case- and connection-version-bound results with ten-minute TTLs. Expiry is enforced before use; DynamoDB physical deletion can take longer. Only IDs in a current search may be previewed. Import uses the exact server-held preview, not client-provided content.
- `aws/imap-api.ts` uses ImapFlow and MailParser only inside Lambda. The hostname resolves on every operation; any private, loopback, link-local, platform, mixed or reserved answer is rejected using the existing public-address policy. The TCP connection is pinned to the validated IPv4 address while TLS verifies the original hostname. Only TLS 1.2+ on port 993 is allowed, with no certificate bypass or proxy.
- Each operation has a 16-second total deadline, shorter connection/greeting/inactivity timeouts, bounded protocol lines/literals and response sizes, and closes its connection when finished. Folders use EXAMINE (`readOnly: true`); source reads use BODY.PEEK. No send, flag, delete, move, append or expunge operations are exposed.
- Message identity includes folder, UIDVALIDITY and UID. Preview verifies UIDVALIDITY and bounds the raw source to 256 KiB before parsing. HTML-to-text conversion and remote-image processing are disabled. HTML and attachments, including attached forwarded messages, are excluded from evidence; text in the actual inline body is retained. Plain-text excerpts are capped at 20,000 characters and labeled when truncated. Credential echoes in returned data fail closed.
- Imported evidence has `source: imap`, its source identity and mailbox/folder/header provenance. The investigation maps it to support evidence. Stable host/mailbox/folder/UIDVALIDITY/UID identity prevents duplicate imports into the same case. Aliases or a server UID reset can result in a different identity; this is not content-based deduplication.

## Customer lookup and collection

`aws/customer-lookup.ts` implements strict `customer_config`, `customer_save_mapping`, `customer_lookup` and `customer_select` actions under the existing evidence endpoint. A customer mapping binds to the selected Supabase project and connection version. Saving requires explicit approval of the ID, full-name and email columns, merges only those columns into the existing approved scope, and preserves other selections. Adding scope invalidates older order mappings, which must be reviewed again. The initial UI suggestion is not approval. Tables with split first/last names can use an order table with a full-name column for this version.

Lookup uses parameter-bound partial name/email predicates, escaping LIKE wildcards and selecting exactly three fields with LIMIT 6. It displays five records and reports truncation/invalid emails. Nothing is selected by name automatically. Private ten-minute lookup snapshots bind matches to workspace, case version, mapping version and Supabase connection version. Selection accepts a saved match ID, never a caller-supplied email. Case edits, expiry, mapping changes and disconnects invalidate selections. Changing the email increments the case revision and clears previous draft approval. Selecting the existing email preserves the case and draft. No message is sent.

`scope: all` removes the IMAP sequence window while keeping TLS/read-only enforcement, response limits, exact envelope-address checks and the 16-second transport deadline. Large or slow folders can fail explicitly; use the faster search range in that case. A Resend-generated email may have no IMAP copy. **Get evidence** in Connections runs independent Stripe, Supabase, Resend and IMAP reads and reports per-source outcomes; it does not silently change an ambiguous/missing customer email, attach evidence or approve a report.
